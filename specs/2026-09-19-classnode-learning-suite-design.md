# ClassNode 课堂三件套设计文档

> 日期：2026-09-19（2026-09-20 修订）
> 状态：待评审
> 范围：学生学习单、探究助手（交互式网页）、学生端三件套外壳与首页

---

## 1. 背景与目标

ClassNode 目前的互动课堂只支持「学生与 AI 智能体对话」这一种活动形态。本次升级把课堂扩展为**三件套**：

| 模块 | 定位 | 状态 |
|---|---|---|
| **学习单** | 学生在线完成教师预先制作的在线任务单 | 新增 |
| **探究助手** | 学生在 classnode 内直接使用教师制作的交互式网页 | 新增（原名「实验助手」，见 §3） |
| **智能学伴** | 原有的智能体对话 | 已有，本次迁入新外壳 |

每个模块由教师以**三态**实时控制（开放 / 预告 / 隐藏，见 §4.4），三件套可任意组合。学生端设**常驻首页**作为课堂门户（见 §4.2）。

### 成功标准

1. 教师能做出含判断、单选、多选、填空、问答、连线、绘图、排序的学习单，可复制复用。
2. 学生能逐题作答并提交，教师能**实时看到每一位学生每一道题的完成情况**。
3. 教师能上传自制网页并关联课堂，学生能直接使用，教师能在**既有看板上**实时看到全班学生的使用画面与操作。
4. 全部功能在**学生端既有设备（含老 iPad / Safari 15）**上可用。

### 设计基调

中小学课堂使用的学习单**不会很复杂，最多 A4 纸正反面**。这条约束贯穿全文：题型少而精、编辑器轻量、不引入教师用不上的概念。

## 2. 范围与分解

需求包含多个相对独立的子系统，**不做单一巨型交付**，拆为 4 个子项目、按 **P0 → P2 → P1 → P3** 顺序推进。

| | 子项目 | 内容 |
|---|---|---|
| **P0** | 学生端外壳与首页 | 常驻首页、Tab 容器、三态控制、状态保留、切换动画；前置清理：拆分 `src/app/classroom/page.tsx` |
| **P2** | 探究助手 | 网页上传托管、源隔离、SDK 注入、实时监控链路、教师看板视图 |
| **P1** | 学习单 | 数据模型、题型注册表、教师编辑器、学生作答与提交、教师进度视图 |
| **P3** | 收口 | 导出、课堂历史、视觉打磨 |

### 为什么 P2 排在 P1 之前

P2 体量只有 P1 的零头，但它会**第一个验证 P0 容器设计是否正确**（状态保留、三态控制、通信、性能、老 iPad 兼容）。若 P0 存在设计缺陷：

- 在 P2 阶段发现 → 返工成本约一天
- 等 P1 全部完成后再发现 → 返工成本约一周

**用小的验证大的。** M1 的性能门槛是硬门槛，不达标就回头改外壳架构，绝不带着问题往下走。

> **实现计划按子项目分别编写。** 本文档是四个子项目的共同设计依据，不应据此产出一份覆盖全部内容的巨型实现计划。每个里程碑各自编写独立实现计划，前一个验收通过后再启动下一个。

## 3. 全局决策记录

| 决策点 | 结论 | 依据 |
|---|---|---|
| 网络环境 | 局域网为主，可访问外网 | 用户环境说明 |
| 模块控制 | 三件套（**含学习单**）统一由教师以**三态**实时控制 | 见 §4.4 |
| 学生端首页 | **常驻门户** | 用户选择 |
| 批改模型 | 客观题**教师可选**是否自动判分；逐题状态**实时**回传 | 用户要求 |
| 提交模型 | **逐题提交**；提交后默认允许修改并重新提交 | 见 §8.4 |
| 分层教学 | **P1 不做**，全班使用同一张学习单（`Classroom.worksheetId` 一对一） | 见 §6.2 |
| 输入方式 | P1 只做键盘 + 手写笔迹（不识别）+ 绘图；语音延后至 P4 | 见 §7.4 |
| 编辑器形态 | 文档流式（题目纵向排列 + 拖拽排序） | 用户选择 |
| 探究助手监控 | 复用**既有学生卡片图墙**，仅切换卡片内容；点击卡片看详情 | 见 §9 |
| 课后回放 | **不做**。截图与操作流水只在内存，课堂结束释放 | 用户否决 |
| 课中变更模块 | 支持实时切换三态 | 见 §4.4 |
| 答卷安全 | 答案不下发学生端 + 服务端判分 | 见 §10.1 |
| 命名 | 学习单 · 探究助手 · 智能学伴 | 用户选择 |

**关于「探究助手」的命名**：三件套并列时「探究**助手**」与「智能学**伴**」在中文里都指"帮你的角色"，区分度低于早前的备选「探究空间」。因教师口头表述「打开探究助手」更顺，故采用现名。

### 明确不做（YAGNI）

- **分层教学**——P1 不做，全班一张
- **课后回放**——不做截图落盘、不做录屏回放
- **手写识别**——不做，笔迹直接作为答案（见 §7.4）
- **语音输入**——P1 不做，延后到 P4
- **材料题组**——不做容器 UI，仅在数据结构中预留嵌套（见 §7.3）
- **公式识别 API**——不引入付费第三方
- **「一次一题」的分步作答模式**——只做整卷滚动
- **候选题型**（分类题、表格填空、标注题、音频题、投票题）——**全部从路线图撤下**，不列优先级、不排期，待教师实际提出需求再评估
- **前端测试框架**——不引入，重逻辑全部放服务端

### 4.2 学生端首页（常驻门户）

学生进入课堂后的**默认落点**，不是直接掉进某个模块。

```
┌──────────────────────────────────────────────────────┐
│  七年三班 · 互动课堂                    互动码 1234   │
│                                                      │
│  ┌──────┐                                            │
│  │ 头像 │  张三                                      │
│  └──────┘  学号 #12                    [ 换头像 ]    │
│                                                      │
│  ────────────────────────────────────────────────    │
│  今天的学习                                          │
│                                                      │
│  ┌────────────────┐ ┌────────────────┐ ┌───────────┐│
│  │ 📘 学习单       │ │ 🧪 探究助手     │ │ 🤖 智能学伴││
│  │ 光合作用探究    │ │ 凸透镜成像      │ │ 小科老师   ││

│  │     [ 继续 ]    │ │     [ 进入 ]    │ │  [ 对话 ] ││

│                                                      │
│  （预告态的模块：卡片显示但灰掉 + 🔒 老师还没开放）   │

```

**内容**：

- 班级名 + 互动码
- 学生本人头像与姓名（点击可换头像，复用现有 `AvatarChanger`）
- **三件套入口卡片**，每张显示模块名、图标、内容摘要、当前状态
  - 学习单：标题 + 作答进度（如「已完成 3/10」）
  - 探究助手：可用网页数量或上次使用的网页名
  - 智能学伴：智能体名 + 最近一轮对话摘要
- 三态呈现见 §4.4

**导航**：从模块返回首页的入口放在 Tab 栏最左侧（课堂名/首页图标）。首页是 `step` 状态之一：

```
step: 'loading' | 'identity' | 'home' | 'shell'
```

**这是「美观、吸引学生」的主要着力点** —— 首页有最大的设计空间，实现阶段调用 `frontend-design` 技能专门设计。

### 4.3 模块契约

模块与外壳之间**唯一**的接口：

```ts
interface ModulePanelProps {
  active: boolean;        // 此刻是否可见
  state: ModuleState;     // 'open' | 'preview' | 'hidden'
  classroom: ClassroomInfo;
  session: StudentSession;
}
```

模块自行响应 `active` 变化（如探究助手在此向 iframe 发送挂起信号）。外壳不关心模块内部；模块不关心有几个兄弟。**加一个模块 = 加一个组件。**

### 4.4 三态控制

**三个模块（含学习单）统一由教师实时控制**，各有三种状态：

| 状态 | Tab 表现 | 卡片（首页）表现 | 教学场景 |
|---|---|---|---|
| **开放** `open` | 可见、可点击 | 正常、可点 | 正常使用 |
| **预告** `preview` | 可见但灰掉，点击提示「老师还没开放」 | 灰掉 + 🔒 角标 | 教师：「等下我们用探究助手做实验，先把学习单第 3 题做完」——学生看得见、有期待，但进不去 |
| **隐藏** `hidden` | 完全不显示 | 不显示 | 这堂课没有这个环节 |

**「预告」态的价值**：让教师能做教学节奏管理，学生知道有这个工具而不必反复询问。三个模块地位平等，学习单也不例外。

**数据模型**：

```
ClassroomModule            # 模块状态（与资源关联解耦）
├─ classroomId
├─ moduleKey: 'learning-sheet' | 'explorer' | 'companion'
├─ state:     'open' | 'preview' | 'hidden'
└─ @@unique([classroomId, moduleKey])
```

> **⚠️ 实现修正（M1b-2 落地时）**：本节原先写的键名是 `module: 'worksheet' | 'explore' | 'companion'`，**与实际落地的代码/数据库不一致**。实现用的是 `moduleKey`，取值为 `'learning-sheet' | 'explorer' | 'companion'`（单一来源：`server/src/services/classroom-module-state.ts`；前端镜像在 `src/lib/classroom-modules.ts`）。**这里已按实现改正**——键名是持久化数据，改了要迁移，所以以代码为准。

资源关联沿用各自机制，与本表解耦（模块可以「预告」但尚未配资源）：

| 模块 | 资源关联 |
|---|---|
| 学习单 | `Classroom.worksheetId`（P1 一对一；将来做分层时改为关联表） |
| 探究助手 | `ClassroomWebApp` 关联表（多对多，学生端在「探究助手」内看到网页列表；仅一个时直接进入） |
| 智能学伴 | `ClassroomAgent`（已有） |

**实时切换**：复用现有 `agent-enabled/disabled` 的广播机制（教师端已向 `classroom:<id>` 房间广播）。

- `preview → open` → 学生端首次挂载该模块
- `open → preview/hidden` → **仅隐藏 + 挂起，不立即销毁**。教师误操作后可零成本恢复；真回收留给课堂结束
- 学生正在使用被关闭的模块时：提示 + 送回首页，**不丢已作答内容**
- **惊群对策**：模块网页资源设长缓存；推送时给学生加 0～3 秒**随机错峰**，避免 40 个 iframe 同时拉取同一份 JS/CSS

**边界情况**：三个模块全部为 `preview`/`hidden` 时，学生停留在**首页**，三张卡片全部灰掉——这正是首页存在的意义之一。

**老课堂升级后的行为（M1b-2 Ruling 1 的裁定结果，回写于此）**：

三态默认值为 `preview`（教学上最保守的起点，与本节的「预告」设计意图一致）。因此在 M1b-2 上线后，**升级前创建的课堂没有任何 `ClassroomModule` 行**，读路径按 `MODULE_KEYS` 补齐 ⇒ **三个模块一律呈现为 `preview`**——学生三张卡片全灰、进不去智能学伴。

**裁定：接受这个行为，并加教师可见提示**，而不是「零行时把 `companion` 视为 `open`」。

- 理由：尊重本节的设计意图；同时不让教师在升级当天困惑于「学生为什么进不去」。
- 实现：教师端课堂看板的「模块状态」菜单里，当三个模块**都**是 `preview` **且该课堂确实没有任何 `ClassroomModule` 行**时，显示一句提示。区分「**查到了零行**」与「**查不到**」是关键——前者才提示，后者（读失败）必须沉默，否则会把一次查询失败误报成「未配置」。
- **若判断有误的代价**：教师在升级当天可能发现学生进不去智能学伴；改动很小（换成「零行时 `companion` 视为 `open`」只需改读路径一处）。

### 4.5 挂载管理

| 状态 | 进入条件 | 行为 |
|---|---|---|
| 未挂载 | 从未访问且非 `open` | 不渲染，零成本 |
| 已挂载·活动 | 当前选中 | 正常渲染 |
| 已挂载·隐藏 | 切走 / 转为 `preview`/`hidden` | 保留在 DOM，`visibility:hidden` |

**模块一旦挂载即不再卸载**（直到课堂结束）。这是「切换保留内容」的实现方式——不卸载就不存在状态丢失。代价是最多 3 份模块内存，由 §4.8 的性能门槛验证。

### 4.6 切换动画

`transform: translateX()` + `opacity` 横向滑动；首页与模块之间、模块与模块之间使用同一套过渡。两面板在动画期间共存，动画**结束后**才给非活动面板加 `visibility:hidden`。

Tab 栏带随选中项平移的指示器滑块，模块以颜色区分：学习单=蓝、探究助手=紫、学伴=青。

### 4.7 Safari 15 硬约束

- 只用 `transform` / `opacity` 做动画（GPU 加速路径稳定）。不用 `filter`、`clip-path` 动画
- 禁用 `:has()`、`content-visibility`、`@container`——Safari 15 不支持且会静默失效
- 遵循 `prefers-reduced-motion`，降级为直接切换

### 4.8 性能预算

| 指标 | 阈值 |
|---|---|
| 首屏可交互 | ≤ 3s |
| 首页 ↔ 模块、模块互切 | ≤ 300ms |
| 三模块全挂载后内存 | ≤ 150MB |
| 探究助手 iframe 空闲 CPU | ≈ 0%（挂起生效） |

必须在**真实老 iPad** 上实测。不达标则回头修改外壳架构。

配套措施：

1. **iframe 挂起协议**——切走时 postMessage 通知，教师网页（若接入 SDK）主动暂停循环；未接入者靠浏览器节流兜底，**但不销毁 iframe**（销毁即丢状态）
2. **消息列表渲染上限**——现有学伴对话全量渲染无上限，改为「默认渲染最近 N 条 + 向上加载更多」。这是已存在的隐患，本次一并修复
3. **低性能降级模式**——一个全局设置项（写入 `Setting` 表，在教师端设置页开关，需重启生效——沿用 `lan-access` 的既有模式）。开启后同一时刻只挂载当前 tab，切走即销毁。**仅作为极端老设备的逃生舱，非默认路径**；开启时须向学生提示「切走会丢失未保存内容」

### 4.9 M0 交付后的实况核对（2026-09-20 补充）

M0 已完成并合入 `feat/classroom-suite`：`page.tsx` 由 2495 行降至 **26 行**，产出 16 个文件。实施过程中整体审查发现**本设计对 M1 的两处预估偏乐观**，M1 排期必须据此修正：

**① M0 并未交付「可挂载的容器」（原假设错误）。**
`chat/chat-panel.tsx` 的 `StudentChatContent()` **不接收任何 props**，且自己拥有 `step` 状态机（`'loading' | 'identity' | 'chat'`）、loading 整页、identity 整页、以及 `router.push('/')` 整页跳转。**M1 无法直接把它挂进 tab。**

M1 的第一项必须是**「编排上移」**：把 `step`、loading 分支、identity 分支、`code` / `classroom` / `selectedStudent` 从 `chat-panel` 提到 `page.tsx` / `shell/`，并把 `useChatSocket`（含 `setStep`、`router`、`setSelectedStudent`、`setMessages`）与 `useStudentSession` 一并上移——因为这些现在会写 `step`、会整页跳转，那是外壳职责而非 tab 职责。

**这是一块独立工作量，比 M0 任何单个任务都大，且无法用机械搬家完成（需要设计 `active` 语义）。** 不要指望在 M1 里「顺手」做掉。

**② 聊天分支有三处页面级副作用未受「是否可见」门控，M1 必踩。**
§4.5 规定模块挂载后不再卸载、非活动模块用 `visibility:hidden` 保留。但当前 `chat-panel.tsx` 中：

- `document.body.style.overflow = 'hidden'` + `documentElement` 同类操作 + `visualViewport` / `resize` / `focusin` / `focusout` 监听：只在 `step !== 'chat'` 时因 early-return 不生效。M1 里学生切到学习单 tab 时 `step` 仍是 `chat`，**整个外壳的滚动会被锁死**
- `autoFocus` 与「AI 回答完成后自动聚焦输入框」的 effect：无 `active` 门，模块挂载即聚焦，iPad 上会**弹出键盘**，而学生可能正在首页或另一个 tab

1. **「课堂已结束」的兜底检测长在面板里，外壳自己没有生命期观察者。** push 路径在 `use-chat-socket.ts:137`，而 15 秒轮询兜底在 `chat-panel.tsx:381-410`。§4.8 的低性能降级模式正是「切走即销毁」——那一刻**只要学生不打开学伴 tab，课堂结束就检测不到**，学生会在已结束的课堂里继续作答。**建议把轮询搬进外壳**（它是会话生命期，不是模块呈现），顺带让 §4.9② 要求的「给它加 `active` 门」变成不必要。
2. **autofocus 的两条路径在保留策略下会双双失效，且失效方向取决于策略。** `visibility:hidden` 下元素**不可聚焦**，`el.focus()` 静默 no-op，iOS 的 `readOnly→focus→readOnly` 技巧一并失效 ⇒ 回到学伴 tab 键盘不再自动弹出（基线是自动弹的）；而 §4.6 动画期的 `opacity:0 + transform` 阶段元素**仍可聚焦** ⇒ 键盘可能弹在另一个 tab 上。**两条路径都要改**（`autoFocus` 属性与 `[waitingAI]` effect）。

4. **「只渲染最近 N 条消息」与现有标记机制相撞。** `data-msg-id` 用的是**渲染数组下标**，而 `updateMarkers`/`scrollToMarker`/`lastUserMessageIndex` 全部基于该下标。`messages` 现在归外壳（全量），一旦面板只渲染切片，标记条位置、点击跳转、`isRespondingToThis` 全部错位。**修法**：标记与跳转改用 `msg.id`/`roundIndex` 做键。
5. **三处 generation 判等都写 `!==`**（`use-chat-socket.ts:56/165/208`），所以「handler 里 +1、卸载清理里再 +1」不互相破坏。**M1b 若把任何一处改成 `===`（读起来更自然），双次自增会开始静默吞掉回调。**
6. **面板卸载清理是 `useEffect(..., [])` + eslint-disable，闭包捕获首帧的 props。** 今天安全（9 个 ref 对象由 `page.tsx` 稳定持有）；M1b 若做成 per-tab 或按会话重建 ref，清理会去复位**旧对象**。

## 5. P2：探究助手

### 5.1 源隔离方案

| 做法 | 网页能用 localStorage | 能读教师 session | 结论 |
|---|---|---|---|
| 同源 iframe | ✅ | ⚠️ 能 | ❌ |
| 同源 + sandbox 无 `allow-same-origin` | ❌ 抛 `SecurityError` | ✅ | ❌ 教师网页功能残缺 |
| **独立源 + `allow-same-origin`** | ✅ 有自己的 | ✅ 跨源天然隔离 | ✅ **采用** |

`allow-scripts` + `allow-same-origin` 组合在**同源**时危险（iframe 可自行摘除 sandbox），但此处 iframe 为**跨源**，无法触达父页面，组合安全。

**实现**：Express 额外监听一个端口（`CLASSNODE_WEBAPP_PORT`，默认 = `CLASSNODE_SERVER_PORT` + 1），仅服务 `/webapps/` 静态资源与 SDK，**不挂任何 API、不带任何 cookie**。该端口故障不影响主服务。

> **集成点**：`dev.sh` 目前拥有全部端口（`CLASSNODE_CLIENT_PORT` / `CLASSNODE_SERVER_PORT`），并在启动时导出给各进程。新增的 `CLASSNODE_WEBAPP_PORT` 必须一并纳入 `dev.sh` 的端口管理与 `status` / `stop` 输出，否则桌面端与开发环境的端口分配会出现不一致。Tauri 侧同样需要为该端口做占用检查。

**sandbox 集合**：`allow-scripts allow-same-origin allow-forms allow-pointer-lock allow-downloads`

**故意不给**：`allow-top-navigation`（防网页跳走整个页面）、`allow-modals`（防 `alert` 卡死老 iPad）

### 5.2 上传

- **ZIP 包**（推荐路径）：复用现有 `safeExtractZip`（`server/src/services/upload-security.ts`）
- **多选文件**：教师选中 `index.html` + `style.css` + `app.js`，首个 `.html` 作入口
- **存储**：`CLASSNODE_DATA_DIR/webapps/<uuid>/`，与现有 uploads 平级，同样受 `CLASSNODE_DATA_DIR` 重定位约束

校验规则（沿用 `upload-security.ts` 风格）：

- 必须含入口 HTML，否则拒绝
- 扩展名白名单：html / css / js / mjs / json / 图片 / 字体 / 音频 / 视频 / wasm
- **拒绝任何服务端脚本**（php / jsp / asp / cgi）——本模块只做静态托管
- 单文件、总大小、文件数三项上限

### 5.3 外部依赖自检

教师可能在网页中使用 CDN 资源（如 `cdn.jsdelivr.net`）。环境为「局域网为主 + 外网可达」，外网正常时无碍，**外网变慢或被限流时该网页会白屏**，而教师会误判为 ClassNode 故障。

**对策**：上传时扫描 HTML / CSS / JS 中的外部 URL，发现即提示「本网页依赖 N 个外部资源，离线环境下可能无法使用，建议将依赖一并打包进 ZIP」。**不阻断上传，仅提醒。**

### 5.4 SDK 注入

托管服务返回 HTML 时，在 `</head>` 前注入 `<script src="/__classnode/sdk.js">`。**教师无需修改自己的网页。**

| 能力 | 说明 |
|---|---|
| 握手 | 与父页面建立 `postMessage` 通道 |
| 事件采集 | `document` capture 阶段事件委托，采集点击元素选择器、滚动深度、页面内跳转、可见性变化 |
| 截图 | 优先直读 `<canvas>`（快）；页面无大 canvas 时按需加载截图库 |
| 挂起协议 | 响应 `onPause` / `onResume`，切走时停掉自身循环 |
| 上报 API | 提供 `ClassNode.report({score, done, step})` 供教师网页调用 |

**隐私红线**：事件采集**默认不采集输入框内容**，仅记录「在某输入框输入、长度 N」。需采集具体内容必须由教师网页显式调用 `ClassNode.report()`。此为面向未成年人的底线，不可放宽。

### 5.5 实时监控链路

```
iframe(SDK) ──postMessage──▶ 学生端父页面 ──socket.io──▶ 服务端内存 ──socket.io──▶ 教师看板
```

- 服务端**只存内存**（每人最新一帧 + 最近事件 + 累计计数），**不落盘**，课堂结束释放
- **按需推流**：服务端维护「有多少教师在看探究助手视图」，归零即通知全体学生停推。教师未开看板时学生端零开销
- **缩略图自清理**：仅保留每人最新一帧（40 人 ≈ 600KB 内存）
- **教师点开某学生时**，可按需单独拉取一张全质量截图（图墙用低质量省带宽）
- **截图降频**：测量截图耗时，超过 300ms 自动降档（5s → 10s → 20s）；`document.hidden` 时完全停发

**唯一落盘项**：课堂结束时写入一条**汇总记录**（谁用了哪个网页、时长、交互次数），用于课后报告。

### 5.6 教师端管理

- **管理页** `/teacher/webapps/`：沿用 `agents/page.tsx` 的卡片网格 + 表单弹窗模式，含**在线预览**（教师自行试玩）与**使用量守卫**（复用 `agents.ts` 的 `GET /:id/usage` 模式，删除前拦截）
- **课堂关联**：新建课堂时勾选

## 6. P1：学习单 — 数据模型

### 6.1 表结构

```
Worksheet              # 学习单（模板，可复用）
├─ id, title, description
├─ subject?, gradeLevel?        # 学科/年级标签
├─ theme?                       # 封面主题色
├─ schemaVersion                # ★ 结构版本号，供题型演进时迁移
├─ content   Json               # 题目结构（嵌套树）
├─ settings  Json               # defaultInputMode、allowResubmit 等
└─ createdAt / updatedAt

WorksheetResponse      # 学生 × 学习单 的作答会话
├─ classroomId, worksheetId, studentId
├─ status: not-started | in-progress | submitted
└─ startedAt / submittedAt / updatedAt

WorksheetAnswer        # ★ 逐题作答——实时看板建于此表
├─ responseId, questionId
├─ value       Json             # 答案（格式见 §6.3）
├─ status: unanswered | draft | submitted     # ★ 三态，见 §8.4
├─ score?, isCorrect?           # 仅开启自动判分且已提交时有值
├─ submittedAt                  # 定稿时间戳（供后续智能体分析）
└─ @@unique([responseId, questionId])
```

**决策 1：`content` 存 JSON，不拆关系表。** 查询模式永远是「取整份学习单」，从不「查第 3 题」。JSON + `schemaVersion` 支持题型演进迁移；关系表则会导致每加一个题型就改一次 schema。

**决策 2：`WorksheetAnswer` 逐题一行。** 40 人 × 20 题 = 800 行/课，SQLite 无压力。实时看板、完成率、错题统计全部由该表聚合，无需额外统计表。

**决策 3：`content` 为嵌套树结构。** P1 不实现容器 UI（见 §7.3），但数据结构预留，以便将来加入材料题组时不需迁移。

### 6.2 分层教学：P1 不做

**P1 全班使用同一张学习单**，`Classroom.worksheetId` 一对一关联，不实现任何分组界面。

> **将来的迁移路径**：学习单若要做分层，把 `Classroom.worksheetId` 改为一张关联表（`classroomId` + `worksheetId` + 可空 `groupId`，与 `ClassroomWebApp` 同构）即可——把现有的一条全班记录转成一条 `groupId = null` 的记录，是一次简单的数据搬迁，**不改任何业务逻辑**。P1 不为这个未来做任何额外设计。

### 6.3 答案的存储格式

每种答案自带 `format` 版本号，**原始数据与识别结果分离**：

```jsonc
// 键盘输入
{ "format": "text/v1", "text": "光合作用" }

// 手写笔迹（不识别）
{
  "format": "ink/v1",
  "strokes": [{ "points": [[x, y, t], ...], "width": 2.5, "color": "#000" }],
  "canvas": { "width": 800, "height": 200 },
  "recognized": null          // ★ P4 智能体识别结果写此处，不覆盖 strokes
}

// 绘图题
{
  "format": "drawing/v1",
  "strokes": [ ... ],         // 矢量
  "canvas": { ... },
  "snapshot": "/uploads/..."  // 位图快照，供列表缩略图
}

// 客观题
{ "format": "choice/v1", "selected": ["A", "C"] }
{ "format": "match/v1",  "pairs": [["L1","R3"], ["L2","R1"]] }
{ "format": "order/v1",  "sequence": ["B","A","D","C"] }
```

**架构要求**（为 P4 智能体分析铺路，使届时几乎零改造）：

1. 笔迹存**矢量点集**，不存截图——截图丢精度，且模型难以处理
2. 每种原始数据带**格式版本号**，便于将来判断能否直接消费
3. 识别/分析结果写入**独立字段**（如 `recognized`），**永不覆盖原始数据**
4. `submittedAt` 标记定稿时刻，供智能体只分析已定稿的答案

### 6.4 教师端 API

```
GET    /api/worksheets                    列表（按学科/年级/关键词筛选）
GET    /api/worksheets/:id                详情（含完整 content）
POST   /api/worksheets                    新建
PUT    /api/worksheets/:id                更新
DELETE /api/worksheets/:id                删除（使用量守卫）
POST   /api/worksheets/:id/duplicate      ★ 复制一份
GET    /api/worksheets/:id/usage          被哪些课堂引用（删除前拦截）
```

全部 `requireTeacher`，在 `index.ts` 注册时统一挂载——沿用项目既有约定，路由自身不加重认证。

**「复制一份」是唯一的复用路径**：深拷贝 `content` 生成新学习单，教师在新副本上修改。不引入「模板」「版本」等额外概念。

## 7. P1：题型与输入方式

### 7.1 题型注册表

```ts
interface QuestionTypeDefinition<T> {
  type: string;                    // 'single-choice'
  label: string;                   // '单选题'
  category: 'objective' | 'subjective' | 'drawing';  // 决定能否自动判分
  defaultData(): T;                // 新建时的初始数据
  Editor: FC<EditorProps<T>>;      // 教师端「编辑态」
  Answer: FC<AnswerProps<T>>;      // 学生端「作答态」——教师预览复用同一个
  grade?(data: T, value): GradeResult | null;   // 客观题才有
  validate?(data: T): string[];    // 编辑校验，如「至少两个选项」
  summarize?(data: T, values[]): Summary;       // 看板聚合口径
}
```

**「学生端作答态」与「教师端预览」是同一个组件**——教师预览所见即学生所见，不可能出现两端不一致。

**加一个题型 = 新建一个文件 + 注册表加一行**，不触碰任何已有文件。

### 7.2 P1 题型清单

| 题型 | 类别 | 自动判分 | 输入方式 |
|---|---|---|---|
| 判断题 | objective | ✅ | 点选（固定） |
| 单选题 | objective | ✅ | 点选（固定） |
| 多选题 | objective | ✅ | 点选（固定） |
| 填空题（行内） | objective | 条件性（见 §7.5） | **教师指定** |
| 问答题（多行） | subjective | ❌ | **教师指定** |
| 连线题 | objective | ✅ | 连线操作（固定） |
| 绘图题 | drawing | ❌ | 手绘（固定） |
| **排序题** | objective | ✅ | 拖拽排序（固定） |

内容块：**说明文字**、**图片**。

**排序题**按用户判断优先于材料题组——语文句子排序、历史事件排序、科学实验步骤都是高频用法，且它是**纯叶节点**，实现成本远低于容器。

### 7.3 材料题组：不做，但结构预留

`content` 树保持**嵌套结构**（每个节点有 `children` 数组）。

成本为零，但将来真要做「一段材料下挂多个小题」时不需要迁移数据。**P1 不实现任何容器编辑 UI。**

### 7.4 手写笔迹保留，不做识别

**决策**：保留手写笔迹作为答案，**不做手写识别**。

理由：

1. **「先存原始数据，处理方式后置」本身是更优的架构。** 笔迹是原始数据，今天采集，明天换任何模型都能重新处理，不因识别方案变更而返工。
2. **效果更好。** 通用手写 OCR API 对公式、图形、中英混排、低年级歪扭字体识别效果差；多模态大模型在这几项上是强项。
3. **笔迹本身即可读。** 教师能直接查看与批改，不识别也不损失功能——这一点与语音有本质区别。

**语音为何不能照搬同一逻辑**：录音本身不是可读答案，教师无法听完 40 段录音。语音要么转文字，要么对学生与教师都无价值；而转文字即意味着 ASR 集成与 iPad Safari 上 Web Speech 不可用的老问题。故**语音延后至 P4**，与智能体分析一起做——同一个多模态模型既能读笔迹也能处理音频，一次对接解决两件事。

### 7.5 输入方式由教师指定

**产品原则**：学生操作必须极简——不提供输入方式切换器，不让学生做选择。

多数题型的输入方式由题型天然决定，**教师无需选择**（见 §7.2 表）。真正需要教师决策的**只有填空题和问答题**。

配置层级：

```ts
// 学习单级：批量默认值
interface WorksheetSettings {
  defaultInputMode: 'keyboard' | 'handwriting';
}

// 题目级：仅 fill-blank / short-answer 有此字段
{ inputMode: 'keyboard' | 'handwriting' }
```

学生端**只呈现教师指定的那一种方式**。

**必须向教师明示的取舍**：

> **填空题设为手写输入后，该题无法自动判分。**

因为笔迹无法与标准答案做字符串比对。教师选择手写时，界面须即时显示该提示。这不是缺陷，而是低年级场景的合理取舍（低年级学生本就难以键盘输入），但教师必须知情。

### 7.6 公式录入

采用**符号键盘 + 手写笔迹兼得**：

- 提供小型数学符号键盘（√ ∑ ∫ ² π 分式等）供键盘输入
- 手写面板的笔迹**原样保留**，教师可看到学生真实书写

不接入付费公式识别 API。

### 7.7 分批交付

| 阶段 | 内容 | 可独立验收 |
|---|---|---|
| **P1a** | 数据模型 + 题型注册表 + 教师编辑器 + 8 种题型 | 教师能做出学习单并预览 |
| **P1b** | 学生作答端 + 逐题提交 + 实时回传 + 键盘输入 + 教师进度视图 | 学生能答题提交，教师看板实时反映 |
| **P1c** | 手写笔迹输入 + 绘图 + 符号键盘 | 输入方式齐全 |

## 8. P1：编辑器、作答与提交

### 8.1 教师端编辑器

文档流式，三块布局：左侧题型面板（按 客观题 / 主观题 / 绘图题 / 内容块 分组）、中间题目流、顶部操作栏（预览 / 保存 / 复制一份）。

必须实现的细节：

- **撤销 / 重做**——教师必然误操作，属刚需而非加分项。以 reducer 管理 `content` 树并维护 undo 栈
- **自动保存草稿**——编辑中每 10 秒或失焦保存一次，避免浏览器崩溃丢失备课
- **属性面板折叠**——每题右侧 `⚙` 展开属性编辑

### 8.2 学生端作答

**整卷滚动** + 顶部进度条（已提交/总题数）+ 右侧收起式题目导航（点数字跳转）。

不做「一次一题」的分步模式——那会使学生失去整卷感，且与教师端文档流形成两套渲染逻辑。

### 8.3 保存链路

学生答的每一题都不能丢：

```
学生改动
   │
   ├─▶ ① 本地 state 立即更新 + 写入 localStorage 队列   ← 零延迟，断网不丢
   │
   └─▶ ② 防抖 1.5s ──HTTP PUT──▶ 服务端落库（status: draft）
                                      │
                                      └─▶ ③ socket 广播 ──▶ 教师看板实时更新
```

**写库走 HTTP 而非复用已有 socket**：`PUT` 天然幂等，重试安全；HTTP 有明确成功/失败语义；答题为低频事件（每秒最多几次，非流式），HTTP 开销可接受。socket 只承担「服务端 → 教师看板」的单向广播。

断网时本地队列持续累积，界面显示「离线 · N 条待同步」；`online` 事件恢复后自动重放。状态指示三态：**已保存 / 保存中 / 离线**。

### 8.4 提交语义

**自动保存 ≠ 提交。** 自动保存解决「防止丢」，提交解决「我答完了，以此为准」。两者并存，各司其职。

**采用逐题提交。** 因为你后期要做的是「对所有学生**某一题**的作答情况进行分析」——这是**按题聚合**，逐题提交恰好让智能体拿到的永远是已定稿的答案，而不会分析到学生改到一半的中间状态。

每题三个状态：

| 状态 | 触发 | 教师看板 |
|---|---|---|
| `unanswered` | — | 空白 |
| `draft` | 自动保存（防抖 1.5s） | `◐ 作答中` |
| `submitted` | 学生点「提交本题」 | `✓` / `✗`（若开启判分） |

**提交时的动作**：判分（若该题开启）→ 记录 `submittedAt` → socket 通知教师看板。

**提交后能否修改**——三层控制粒度：

| 层级 | 控制 | 默认 |
|---|---|---|
| **学习单设置** | `settings.allowResubmit`：本单提交后是否可改 | **允许**（符合练习/任务单的多数场景） |
| **课堂控制** | 「锁定作答」按钮：一点全班都不能改，对应「停笔、收卷」；可解锁 | 未锁定 |
| **逐题提交** | 学生标记某题定稿 | — |

允许重新提交时，学生改动已提交的题 → 状态回到 `draft` → 再次提交时重新判分并更新 `submittedAt`。

## 9. 教师看板

### 9.1 复用既有图墙，而非新建

**现有看板已有一面学生卡片图墙**（`src/app/teacher/classroom/page.tsx`）：

```css
.student-grid { grid-template-columns: repeat(auto-fill, minmax(250px,1fr)); gap: 14px }
```

每张卡片高 260px，含头像+姓名+学号+组徽章 → 4 个操作图标（黑屏/发消息/奖励/清除）→ 状态徽章行（`深度思考`/`在线`/`思考`/`离线` + `N 轮` + 奖励⭐ + 警告⚠）→ 最近一轮 Q&A 预览。点击卡片 → 右侧滑出 **420px 浮动抽屉**看完整对话。另有「全屏网格模式」可调 2–8 列。

**探究助手与学习单不新建图墙，而是复用这面墙、只切换卡片主内容区**：

```
┌─ 学生卡片图墙（骨架完全不动）──────────────────────┐
│  [ 学习单 ] [ 探究助手 ] [ 智能学伴 ]   ← 新增：模块切换 │
│  ○全部 ○在线 ○互动中 ○需关注 ○离线      ← 现有筛选胶囊  │
│  ┌─────┐┌─────┐┌─────┐┌─────┐                        │
│  │卡片 ││卡片 ││卡片 ││卡片 │  ← 只换中间那块主内容区   │
│  └─────┘└─────┘└─────┘└─────┘                        │
└───────────────────────────────────────────────────┘
        ↓ 点击卡片
   现有那个 420px 右侧抽屉，内容随模块变
   ├─ 智能学伴 → 完整对话（现状不变）
   ├─ 探究助手 → 大图 + 实时操作流水
   └─ 学习单   → 该生逐题作答详情
```

**理由**：

- 头像、姓名、状态点、4 个操作图标、点击→抽屉、全屏网格、筛选胶囊——**这套交互对三个模块全都适用**，无需重写
- 教师**学习成本为零**：还是那面墙，还是点开看详情，只是卡片里显示的东西变了
- 现有「全屏网格 + 列数调节」正好解决缩略图看不清的问题——切到全屏、调成 4 列即是一面监看墙

### 9.2 卡片主内容区

| 模块 | 卡片主内容 | 卡片高度 |
|---|---|---|
| 智能学伴 | 最近一轮 Q&A 预览（现状） | 260px（不变） |

## 10. 安全设计

### 10.1 答卷安全 — 答案不下发学生端

`content` 中含正确答案与解析（自动判分所必需）。若原样下发学生端，学生用浏览器开发者工具即可看到全部答案。

**定死两条：**

**① 服务端在学生端接口剥离答案字段。**
- 教师端 `GET /api/worksheets/:id` 返回完整版
- 学生端走独立端点 `GET /api/worksheets/:id/student-view`，服务端返回前摘除 `correctAnswer` / `answer` / `explanation` 等字段
- **过滤在服务端执行，不在前端**——前端过滤等同于未过滤

**② 判分在服务端。**
学生提交某题 → 服务端以注册表 `grade()` 计算 → 仅返回 `{isCorrect, score}`。学生端全程无法获得正确答案。

代价是对错显示有数百毫秒延迟，课堂练习场景可接受。

> 备选：若判定为纯练习、可接受答案暴露，可改为前端判分以获得零延迟反馈。**当前设计采用服务端判分。**

### 10.2 探究助手隔离

见 §5.1。要点：独立源 + 最小 sandbox + 不携带 cookie + 不挂 API。

### 10.3 未成年人数据

- 事件采集**不采集输入框内容**
- 截图只在内存保留最新一帧，不落盘、不可回放
- 课堂结束即释放全部监控数据，仅保留一条汇总记录

## 11. 兼容性

### 11.1 扩展构建期检查

现有 `scripts/check-classroom-browser-compat.mjs` 仅拦截 regex lookbehind。本次将编写**大量新前端代码**，一个漏网即白屏。建议扩展覆盖以下 Safari 15.4 才支持的 API：

`Object.hasOwn` · `structuredClone` · `Array.prototype.at` / `findLast` · `:has()` · `@container` · `content-visibility` · `dvh` 单位 · `:focus-visible`

扩容本身工作量很小（正则扫描 + 构建期失败），但会在整个 P0–P2 期间持续兜底。**这是本次升级中性价比最高的一项改动。**

### 11.2 已验证可用

`MediaRecorder`（P4 语音用）、Pointer Events（手写）、`ResizeObserver` 在 Safari 15 上均可用，无需替代方案。

### 11.3 其他既有约束

- HTML 必须保持 `no-store`、`_next/static/` 才用 immutable 缓存（见 CLAUDE.md）
- 学生端不得出现 regex lookbehind

## 12. 错误处理

| 场景 | 处理 |
|---|---|
| 探究网页加载失败 / 白屏 | iframe `onerror` + 超时检测 → 友好提示 + 重试按钮，不让学生卡在白屏 |
| 网页依赖的外网 CDN 失效 | 上传时已预警（§5.3）；运行时检测长时间空白则提示教师 |
| 学习单保存失败 | 本地队列保留 + 自动重试 + 顶部显示「离线 · N 条待同步」，**绝不静默丢数据** |
| 教师课中把模块切为预告/隐藏 | 提示 + 送回首页，**不丢已作答内容** |
| 三模块全部非开放 | 学生停留在首页，三张卡片呈灰态 |
| 手写输入异常 | 笔迹完整保留，可重试，不丢已写内容 |

## 13. 测试策略

现有测试位于 `server/src/tests/`，以 `node --test` 运行。本次新增：

| 测试项 | 说明 |
|---|---|
| **题型注册表 `grade()`** | 纯函数，最值得测。覆盖判分边界：多选漏选是否算对、填空题多个正确答案、连线题部分正确的给分口径、排序题部分正确。**判分错误教师会发现但难以定位，故必须有自动化用例** |
| **答案 value 序列化往返** | 各输入方式产生的结构均需可存可取 |
| **学生端 content 过滤** | ★ 安全测试：断言 `student-view` 返回的 JSON **不含任何答案字段**。必须自动化 |
| **提交状态机** | `unanswered → draft → submitted → draft`（允许重提交时）的转换与 `submittedAt` 更新 |
| **模块三态解析** | 三态取值、默认值、存档读取的兼容性 |
| **API 鉴权** | 学生 token 不得访问教师端 worksheet 端点，也不得调用教师端的模块控制端点 |

**不引入前端测试框架。** 前端逻辑保持薄，重逻辑（判分、过滤、状态机）全部放服务端，天然纳入现有测试体系。

## 15. 后续演进（P4，不在本次范围）

### 15.1 分析型智能体

新增一类**专用于分析学习单作答的智能体**：对所有学生某一题的作答情况做智能分析与统计，甚至给出对学生的指导建议。

**架构方向：扩展现有 `Agent`，而非新建模型。**

```
Agent
├─ purpose: 'tutoring' | 'analysis'   # ★ 新增，默认 'tutoring'
└─ ...（其余字段不变）
```

理由：底层是同一件事——调用 AI 平台 API。`ai-proxy.ts` 的平台适配（Coze / 文心 / 智谱）、`crypto.ts` 的密钥加密、连通性检查、管理页 UI **全部可复用**。新建独立模型意味着把这套适配代码复制一遍。

配套调整：

- 学生端 `ClassroomAgent` 只关联 `purpose = 'tutoring'` 的智能体
- 教师端管理页按 `purpose` 分组或加筛选
- 三件套的「智能学伴」模块只呈现 `tutoring` 类

**待 P4 细化的问题**（本文档不展开）：分析结果的存储结构、教师端呈现形态、触发时机（逐题提交后自动 / 教师手动发起 / 课后批量）。

### 15.2 智能体分析学生作答

将学生的手写笔迹（未来含语音）交由分析型智能体识别并分析。

**本文档已为其预留**：

- 笔迹以矢量点集存储，带 `format` 版本号（§6.3）
- `recognized` 字段独立存在，分析结果不覆盖原始数据
- `submittedAt` 标记定稿时刻，可只分析已提交的答案
- 逐题提交（§8.4）保证智能体拿到的是定稿答案，而非中间状态

届时几乎无需改造既有数据结构。

### 15.3 语音输入

与智能体分析一并实现——同一个多模态模型既可读笔迹也可处理音频。

### 15.4 其他

- **分层教学**（见 §6.2 的迁移路径）
- **材料题组**（`content` 树已预留嵌套结构）
