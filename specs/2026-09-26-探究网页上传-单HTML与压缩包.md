# 探究网页上传：单 HTML 成默认，压缩包扩到 zip / rar / 7z

## 一句话

「添加探究网页」的两栏对调：左边是**单个 HTML 文件**（默认、推荐），右边是**压缩包**（zip / rar / 7z）；「多选文件」那条路整条删掉；单 HTML 上传后如果引用了不在包里的本地文件，明确告警。

- `archive` 分支**显式拒绝非 .zip**（`:563`，「网页压缩包必须是 .zip 文件」），解压走 `safeExtractZip(zip, dest, WEBAPP_LIMITS)`。

## 本次实测结论（新数据，全部来自 `/tmp/7z-probe` 的一次性探针）

**能用的：**

- `7z-wasm@1.2.0`（基于 7-Zip 24.09，1.8MB）。编解码器表里明确列着 `Rar1 / Rar2 / Rar3 / Rar5`，标志位 `D` = **只解不压**。
- 本机一个**真的教师资源包**（RAR5、`v6:512K:m3`、2.1MB）：**13/13 条解出**，与系统 `7zz` 基准逐条一致，**19ms**。中文目录名、全角冒号 `活动2：AI发展图谱…`、带空格的 `图 1.png`、两级嵌套目录全部完好。
- **Node 24 + ESM + `createRequire` 加载得起来**（服务端是 ESM，这是硬前提）。
- 并发 4 个实例互不干扰（13ms）。
- **加密包不会挂住服务端** —— 我原本最担心 7-Zip 停在 stdin 上等密码；实测给不给 `-p` 都是 ~10ms 内失败返回。
- **符号链接被摊平成普通文件**（用 libarchive 那条含 `testlink` 的 RAR3 样本验的：出来是 8 字节普通文件，内容是链接目标）—— 与现有 ZIP 路径的行为一致，**不是退步**。
  - 🔴 **但这是 `7z-wasm`（wasm 构建）的行为，不是 7-Zip 的普遍行为。** T1 实测：本机原生 `7zz` 26.03 解同一个样本，得到的是**真符号链接**（`lrwxr-xr-x testlink -> test.txt`，`Attributes = lrwxrwxrwx`）。
  - ⇒ 两条后果，后面的人别搞反：① **不许**把「7-Zip 会摊平」当保证来依赖 —— 这是**观察到的**行为，一次 `7z-wasm` 升级就可能变；② 因此 `walkExtracted` 里那个 `lstat` + `isLink` 判据**是主保证，不是深度防御**，`safeExtractArchive` 里那句「软链必须看成软链」的注释不许删。

**是问题的：**

- 🔴 **`callMain` 的报错方式不可靠，必须三条一起做。**
  - 把 `.jpg` 改名成 `.rar`：**不抛错**，返回码 `2`，打印 `Cannot open the file as archive`，`/out` 空。**只看 `try/catch` 就是「上传成功、学生打开一片空白」。**
  - 头部加密的 `.7z`：**抛的是一个数字 `262608`**，不是 `Error` 对象。
  - ⇒ `try/catch` + **检查返回码** + **「解完 0 个文件直接判失败」**，三条缺一不可。
- 🔴 **内存**：解一个**解压后 120MB** 的包，进程 RSS 从 46MB 涨到 **1184MB**（~10x），解压本身 163ms、**返回码 0**。我们的上限是 80MB ⇒ 卡在上限就是一个 ~800MB 的进程，而这是装在教师笔记本上的桌面应用。
  - ⇒ **两阶段**：先列表拿声明体积，超限就拒，再解压。
- **`l -slt` 的文本输出会把非 ASCII 文件名弄成乱码**（`图片` → `￥ﾛﾾ￧ﾉﾇ`，UTF-8 字节被当半个假名读了）。**但内存 FS 里的文件名是正确的**（.7z/.zip/.rar 三种都验过）。
  - ⇒ 列表那一步**只读体积 / `Encrypted` 标记 / 条数，路径一律从解压后的 FS 取**。
- **带 `../` 的条目，7-Zip 是「静默剥离」而不是拒绝**（实测 `../../escaped.txt` → `/out/escaped.txt`，返回码 0）。⇒ 这条路上的「路径穿越」**不是我们在挡**，见下面的「硬约束」。

## 设计

### 一、弹窗（`webapp-form.tsx`）

- 两栏对调成 `[['html','单个 HTML 文件（推荐）'], ['archive','上传压缩包']]`，**默认 `'html'`**。
- 两个 `<input type="file">` **都不带 `multiple`** —— 教师要的第 3 条就是这个，带上 `multiple` 就等于把删掉的那条路从侧门放回来。
- 单 HTML 那栏：`accept=".html,.htm"`，一段浅蓝说明 —— 「适合把 CSS / JS 都写在这一个文件里的网页。网页里有子目录（`css/`、`js/`、`images/`）的，请用压缩包。」
  - ⚠️ **这句必须说「都写在这一个文件里」，不能只说「单个 HTML 文件」**：引用外部文件的单 HTML 是能传上去的，只是打开会缺样式 —— 那正是下面第四节的告警要接住的情况，而文案是第一道。
- 压缩包那栏：`accept=".zip,.rar,.7z"`，说明改成「支持 ZIP / RAR / 7Z。解压后目录结构原样保留，`css/`、`js/`、`images/` 子目录都能正常加载。」
  - ⚠️ 现在那句「**请把网页文件夹压成 ZIP 再上传**」必须改 —— 它会把教师往 zip 上引，而这次恰恰是要放开三种。
- **删掉** `files` 这个 `UploadMode` 分支、它的 amber 警告块（`:188-198`）、`files` / `filesSummary` 两个 state、`mode === 'files'` 那两处 `form.append`。
- **单 HTML 模式下隐藏「入口文件（选填）」**：包里只有一个文件，服务端直接取它当入口，这个输入框没有可填的东西，留着只是给教师一个填错的机会。压缩包模式下保持现状。
- 提交时 `mode === 'html'` → `form.append('page', file)`；`mode === 'archive'` → `form.append('archive', file)`。
- 上传成功后，除现有的 `WebappExternalDepsNotice` 外，多渲染一条缺失引用提示（见第四节）。

### 二、服务端 `POST /api/webapps`（`routes/webapps.ts`）

字段收敛成三选一，**`files` / `files[]` 整条删掉**（`upload.fields` 里的两项、`CollectedUploads.loose`、`:580` 那条分支、`discardUploads` 里对 `loose` 的遍历、「请选择要上传的网页压缩包（.zip）或网页文件」那句）。

| 入口 | 字段 | 处理 |
|---|---|---|
| 单个 HTML | `page`（单文件） | `decodeUploadName` → `validateWebappUpload([{path, size}])` → `resolveInDir` → `writeFileSync(..., {mode: 0o600})` |
| 压缩包 | `archive`（单文件） | 后缀必须是 `zip`/`rar`/`7z`（否则 400，文案逐个点名三种）→ `await safeExtractArchive(...)` |

- ⚠️ 单 HTML **必须先 `validateWebappUpload` 再落盘**，顺序与旧的多选那条路一致 —— 它挡的是 `../../evil.html` 这种被构造出来的 `originalname`；`resolveInDir` 是第二道。
- ⚠️ 单 HTML **复用同一段尾巴**（`findSymlinks` → `pruneMacMetadata` → `hoistSingleRoot` → `walkTree` → `validateWebappUpload` → 扫描 → 建库），**一行特例都不加**。第二遍 `validateWebappUpload` 是幂等的。
- `multer` 的 `limits.files` 从 `WEBAPP_LIMITS.maxFiles` 收到 `2`（最多就是 `page` + `archive` 各一个），`limits.fileSize` 保持 `maxTotalBytes`。
- 响应加一个字段：`missingRefs: { count: number; refs: string[] }`（见第四节）。与 `externalDeps` 并列。

### 三、解压服务 `services/archive-extract.ts`（新增）

```ts
export type ArchiveKind = 'zip' | 'rar' | '7z';
export function archiveKindOf(filename: string): ArchiveKind | null;

export async function safeExtractArchive(opts: {
  sourcePath: string;
  originalName: string;
  destination: string;
  limits: ArchiveLimits;          // 与 ZipLimits 同一形状
}): Promise<{ kind: ArchiveKind }>;
```

> ⚠️ 返回值**收窄过一次**（写施工计划时定的）：原先写的是 `{ kind, fileCount, totalBytes }`，
> 但调用方（`POST /api/webapps`）解压后本来就 `walkTree(dest)` 一遍去跑 `validateWebappUpload`，
> 再返一次计数是**同一件事的第二份口径**。少一个会漂移的东西。

**这是 webapp 那条路唯一的解压入口。** `export.ts` 那三处 `safeExtractZip` 调用**不要动**（它们是备份恢复，各自有 1GB / 300MB 的上限，且 `/backup/upload` 需要在解压前读条目名）。

- `kind === 'zip'` → `new AdmZip(sourcePath)` + **现有 `safeExtractZip` 原样调用**。
- `kind === 'rar' | '7z'` → 7z-wasm，六步：

  1. **列表**：`callMain(['l','-slt','-ba','/in/a'])`。`try/catch` 包住（它可能抛**数字**），**并检查返回码**。
     - 失败 ⇒ 400「压缩包读不了（可能是加密的或已损坏）」。**头部加密的 7z 就死在这一步**。
     - 解析出：条目数、目录数、**声明体积之和**、任一 `Encrypted = +`。
     - `Encrypted = +` ⇒ 400「不支持带密码的压缩包」。
     - 超 `maxFiles` / 单个超 `maxSingleFileBytes` / 总量超 `maxTotalBytes` ⇒ 400，**在这一步就拒，绝不进解压**（这是内存那一条的对策）。
     - ⚠️ **只取数字与标记，不从这里读路径**（中文会乱码）。
     - 🔴 **也绝不能从这里读权限位 / 判软链。** 实测 `Attributes` **不可靠，且不同格式下行为不一致**：那个 RAR 样本在 `7z-wasm` 下是 `Attributes = `（**空**）、在原生 `7zz` 下是 `lrwxrwxrwx`；而一个 `.7z` 包在 `7z-wasm` 下是 `A -rw-rw-rw-`（有值）。拿它当软链判据，空值那一档会**静默放行**每一个软链，有值那一档给的是与真实权限无关的假信息。⇒ 这一步只准读**体积 / `Encrypted` / `Folder`**；软链检测**只**能落在第 5 步解压后的 `lstat` 上。
  2. **解压**：`callMain(['x','/in/a','-o/out','-y','-p','-bso0','-bse0'])`，同样 `try/catch` + 检查返回码。`-p`（空密码）是**必须的** —— 让加密包快速失败，而不是停在 stdin 上。
  3. **零文件判失败**：`/out` 里一个文件都没有 ⇒ 400「这不是一个有效的压缩包」。**这一步不能省**（假 `.rar` 的返回码是 0 或 2 都可能，见实测）。
  4. **交叉核对**：FS 里的文件数与体积之和，与第 1 步的声明值比对，对不上 ⇒ 400（挡「头部撒谎」的包）。
  5. **遍历**：用 **`FS.lstat`**（不是 `stat`，软链必须看成软链）。发现软链 ⇒ 400。逐条校验路径：不许绝对路径、不许 `..` / `.` / 空片段。
     - 🔴 **这一步是主保证，不是深度防御**（这一句在初稿里写反了，T1 实测纠正）。`7z-wasm` 摊平软链这件事**只是一次观察**，不是 7-Zip 的契约 —— 原生 `7zz` 就不摊平。所以「软链到不了磁盘」这件事**由这一步兜着**，不能靠上游行为。
     - ⚠️ **这一步是深度防御，不是主防线。** 主防线是「解压发生在 wasm 的内存 FS 里，除了我们第 6 步自己拷出去的字节，**没有任何东西能落到真实磁盘上**」。`../` 是 7-Zip 自己剥离的，我们事后连原始名字都看不到。
  6. **拷出**：`writeFileSync(target, buf, { mode: 0o600 })`，逐条再核一次体积。

- 内存：实例用完释放，但**实测内存不会立刻还回来**（46MB → 65MB 解一个小包后不降）。上传是低频操作，可接受；**不要为每个请求常驻一个实例**，也不要池化。
- ⚠️ **残留风险（写进代码注释，不要假装没有）**：第 1 步的声明体积若撒谎，第 2 步仍会按真实体积展开。**现有 AdmZip 那条路有同样的暴露**（`safeExtractZip` 也是先 `getData()` 物化、再比对长度），所以这不是新增的退步。

### 四、单 HTML 的「引用了但不在包里」（新增扫描器）

放在 `services/` 下，与 `webapp-external-deps.ts` 同族：`scanMissingLocalRefs(files, presentPaths) → { count, refs }`。

- 识别的引用：`href` / `src` / `srcset` / `url()` / `@import` 里的**相对路径与站点内绝对路径**。
- **不算缺失**：`http(s):` / 协议相对 `//` / `data:` / `blob:` / 纯 `#片段` / 纯 `?查询` / `mailto:` `tel:` `javascript:`。
- **对两种模式都生效**，不特判单 HTML：单 HTML 只是「在场文件集合 = 1 个」的退化情形。同一份代码、同一套用例。
- ⚠️ **已知粗糙（沿用 `scanExternalDeps` 那条「误报优于漏报」的方针，别再论证一遍）**：动态拼出来的路径（`fetch('./data/' + id + '.json')`）会被报成缺失。**这条提示不阻断上传**，措辞必须写成「**疑似**引用了…这些文件不在这份上传里」，不能写成断言。
- 前端呈现：与 `WebappExternalDepsNotice` 并排的第二条提示（同一种黄框），标题「这个网页引用了 N 个不在包里的文件」，正文列 `refs`（截断到 6 条 + 「等 N 个」）。**文案要说出后果**：「学生打开时这些会加载失败，网页可能没样式。」

### 五、依赖与打包

- `server/package.json` 加 `7z-wasm`（普通 dependency，不是 devDependency）。
- `scripts/package-server.mjs` 的 `requiredFiles` 加一条 `node_modules/7z-wasm/7zz.wasm`。
  - 🔴 **这条不是可选的**：不加的话，打包少一个 wasm 文件这种事**只会在教师机器上以运行时错误暴露**，而这正是那张清单存在的理由。
- 纯 JS + wasm，**没有平台二进制** ⇒ `build-mac.sh` / `build-windows.sh` / GH Actions **不需要**为此加任何按架构的分支。

## 硬约束（照着做，别踩）

1. **`export.ts` 那三处 `safeExtractZip` 一行都不许动。** 其中 `/backup/upload` 需要在**解压前**逐条读条目名做白名单（`:792`），1GB 上限那条走 7z-wasm 会在内存上直接死。
2. **不许把 `adm-zip` 从 `package.json` 里删掉** —— 它还有四个生产调用点。
3. **两个文件输入框都不许带 `multiple`。**
4. **`callMain` 的三条防线缺一不可**：`try/catch` + 返回码 + 零文件判失败。少任何一条都会造出「上传成功但打开空白」。
5. **列表那一步不许拿路径做任何判断**（中文乱码）。
6. **先列表再解压**，不许把体积校验挪到解压之后。
7. 单 HTML 走**同一段尾巴**，不许为它加特例分支。
