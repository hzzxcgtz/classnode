## 一句话

把题干的格式从**整段一份**改成**按区间标**，编辑面从 `<textarea>` 换成**所见即所得**
（contenteditable）。

**这不是加两个按钮。** 现在 `promptStyle` 是整段一个对象，而「只对选中的一段设置」
要求格式能落在**文字的某一段**上 —— 那是内容结构变了。

## 数据模型

`prompt` 仍是**唯一的那份文字**；格式是挂在它上面的**批注**：

```ts
// data.promptRuns —— ★ 施工时改过形状，见下
interface PromptRun {
  start: number;        // 含
  end: number;          // 不含
  bold: boolean;
  italic: boolean;
  underline: boolean;
  emphasis: boolean;    // 着重号
  color: string;        // 取自 WORKSHEET_TEXT_COLORS 的 5 个值
}
```

🔴 **这一节是施工时改掉的（ruling）**：本节原先写的是 `promptMarks` —— 一个
**可选标记的列表**（`[{start, end, bold?: true}, …]`，几条可以叠在一起）。那个形状里
「同一个字段的两条区间压在一起时听谁的」是一个**没有正确答案**的问题，而它的典型结局是
「屏幕上画的和判据算的不一样，且两边都不报错」。
改成 **`promptRuns`：一份分段** —— 有序、两两不重叠、**正好拼满** `[0, text.length)`，
每条带**完整**的五个字段。任一位置**恰好**属于一条，那个问题就不存在了。
代价：库里会显式存下「默认样式」那几条（短题干上就是一条 `{start:0,end:N}`），
换来的是读 / 写 / 渲染三处都不必再处理「没有分段」这种额外情形。

🔴 **三条不变量**（不定死，渲染端就会有一种「谁赢说不清」的情况）：

1. **区间互不重叠、拼满整段。** `setStyleOnRange` 先把重叠的切开再合并 ——
   「谁赢说不清」在这里不存在（这正是换成 `runs` 那个形状的全部理由）。
2. **`color` 与布尔字段不同**：它有一个**值**，所以同一段文字上只能有一个颜色；
   后设的**覆盖**（不是并存）。
3. **区间必须夹在 `0..prompt.length` 内**，且 `start < end`。越界 / 坏值一律**丢掉**
   （读的一侧不信任库里的东西：`readPromptRuns` 负责归一化，抛出去是整块面板白屏）。

## 纯逻辑（`src/lib/worksheet-prompt-marks.ts`）—— 本次的重心

🔴 本仓没有 jsdom、没有浏览器：**JSX 里的判据一条都没有回归网**。所以能算的全部下沉到这里，
由 `node --test` 钉住（先例：`worksheet-drag.ts`、`worksheet-editor-core.ts`）。

| 函数（`src/lib/worksheet-prompt-marks.ts`，**零 import**） | 判据 |
|---|---|
| `readPromptRuns(raw, text)` | 归一化成那一种形状：越界夹紧、坏值丢掉、空隙补默认、重叠时**左边赢**、相邻同款合并 |
| `styleAt(runs, index)` | 光标处的样式；落在**文本末尾之后** ⇒ 最后一条（刚设完格式接着打字要接着它） |
| `rangeHasKey` / `rangeColor` | 选区**整段**都有吗（决定按下去是「设上」还是「取消」）/ 颜色一致吗 |
| `setStyleOnRange(runs, text, from, to, patch)` | 先切开、再写、最后合并；`color` 是**覆盖**；没变就返回**入参本身** |
| `remapRuns(runs, prevText, nextText)` | 编辑之后挪区间（公共前/后缀定位） |
| `promptRunStyle(run)` | 行内样式映射 —— 🔴 **着重号那两个 `-webkit-` 属性名有用例钉着** |
| `isPlainRuns(runs)` | 全是默认 ⇒ 写库时那个键不写 |

**`remapRuns` 的归属规则**：被替换的区间 `[from, oldTo)` 里新插入的文字取
「**替换点前一个字符**」的样式（不是「替换点那一条」= 后一个字符）—— 取后一个会让
「在加粗段末尾接着打字」掉出加粗段，教师看来像是加粗被吃掉了。
⚠️ 已知边界：公共前/后缀法在「改完和原来长得一样」时（`aa` → `aaa`）分不清编辑发生在哪，
一律归到**靠后**的位置。纯外观，不丢字。

## 渲染：一个实现，三处用（`src/lib/worksheet-prompt-text.tsx`）

导出 `<PromptText text runs />`，**只用行内样式、不带任何 CSS 模块类** —— 两个调用方分属
两套 CSS（学生端 `worksheet.module.css` 受 Safari 15 门禁扫，教师端 `globals.css`），
基线（字号 / 行高 / 默认色 / 换行）留给调用方那个元素的类。

消费者：**学生端面板**、**编辑页折叠预览**。两处必须走同一份实现 —— 否则就是本仓最防的
那种「预览里画得出来、学生那里画不出来，且两边都不报错」（这条以前真的存在：题干的渲染
原本有**两份**，本次顺手并成了一个）。

着重号：`-webkit-text-emphasis: filled dot` + `-webkit-text-emphasis-position: under`
（⚠️ **必须带前缀**）。⚠️ **中文字体的着重号字形不稳定** —— 有些字体根本不画。
这一条**只能真机看**，见下面的真机清单。

## 🔴 contenteditable 的五条硬约束（本次最大的风险）

裁定 ① 选的是三条路里**唯一会碰到中文输入法**的一条。下面五条不是「最好这样」，
是「少一条就会坏」：

1. **React 永远不许重渲这个框的子节点。** 内容只由 JS 写（`renderRunsInto`，用
   `createElement` + `textContent` —— **不拼 HTML 字符串**，题干里一个 `<` 就能把结构吃掉）。一旦 React 按 state 重画，
   输入法拼字会被打断 —— 🔴 **症状是「这个框没法打中文」**，而这个仓的用户全是中文教师。
2. **拼字期间（`compositionstart` → `compositionend`）一个字都不许回写**：不写 DOM、
   不让这个框跟着 setState 重渲。判据用 `event.nativeEvent.isComposing`。
   **这是唯一一条会让字段彻底不可用的约束。**
3. 🔴 **⌘Z 走的是本仓自己的历史栈**（`edit/page.tsx:178` 上面那段注释写着：那里**有意**
   抢掉浏览器的撤销，因为本仓每次改动一条、退掉的正是上一个字符）。它会把 `prompt` 换掉
   ⇒ 编辑器必须**把 DOM 重建成新文本**，并把光标放回一个**夹紧到新长度**的位置。
   ⚠️ 这件事 `<textarea>` 是**白拿的**（React 换 `value`，浏览器自己管光标），换成
   contenteditable 之后要自己做 —— **撤销之后光标跳回开头**就是漏了这一条的症状。
4. **换题（`node.id` 变了）整块重建**，不要试图 diff。
5. 保存仍走既有的 `onPromptChange` / `onDataChange` 与防抖队列，一个字节都不改。

⚠️ **键盘守卫**：`edit/page.tsx:198` 的 `↑/↓` 判据认的是 `[contenteditable="true"]` ——
React 写 `contentEditable` 会渲染成 `contenteditable="true"`，**对得上**；
写 `contentEditable=""` 就**对不上**，症状是打字时按上下键跳到别的题。
