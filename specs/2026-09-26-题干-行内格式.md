# 题干的行内格式（下划线 / 着重号 / 选中一段再设）

> 日期：2026-09-26 · 状态：**设计已定，未动代码** · 来源：教师截图 + 一句原话
>
> 「需增加下划线和着重号，并且可以**只选择下面的部分文字**来设置。」

---

## 一句话

把题干的格式从**整段一份**改成**按区间标**，编辑面从 `<textarea>` 换成**所见即所得**
（contenteditable）。

**这不是加两个按钮。** 现在 `promptStyle` 是整段一个对象，而「只对选中的一段设置」
要求格式能落在**文字的某一段**上 —— 那是内容结构变了。

## 教师已裁定的两条（本次全部依据）

| # | 问题 | 裁定 |
|---|---|---|
| ① | 用哪种编辑方式 | **换成所见即所得编辑器**（contenteditable）—— 三条路里体验最好、风险最大的一条 |
| ② | 没选中文字时点 B / 下划线 / 着重号 | **什么都不做**（语义只有一种：这些按钮永远只管选中的那一段） |

⚠️ 裁定 ① 是教师**看过三条路的代价之后**选的（另外两条是「文本框+下方预览」「文本框+镜像层」），
本规格把它的风险如实写在下面，不因已选定就轻描淡写。

## 数据模型

`prompt` 仍是**唯一的那份文字**；格式是挂在它上面的**批注**：

```ts
// data.promptMarks
interface PromptMark {
  start: number;        // 含
  end: number;          // 不含
  bold?: true;
  italic?: true;
  underline?: true;
  emphasis?: true;      // 着重号
  color?: string;       // 取自 WORKSHEET_TEXT_COLORS 的 5 个值
}
```

🔴 **三条不变量**（不定死，渲染端就会有一种「谁赢说不清」的情况）：

1. **同一字段的区间互不重叠。** `setMarkOnRange` 先把重叠的切开再合并 ——
   两条 `bold` 压在一起时「听谁的」是一个没有正确答案的问题。
2. **`color` 与布尔字段不同**：它有一个**值**，所以同一段文字上只能有一个颜色；
   后设的**覆盖**（不是并存）。
3. **区间必须夹在 `0..prompt.length` 内**，且 `start < end`。越界 / 坏值一律**丢掉**
   （照 `readPromptStyle` 那套容错口径：读的一侧不信任库里的东西）。

## 纯逻辑（`src/lib/worksheet-prompt-marks.ts`）—— 本次的重心

🔴 本仓没有 jsdom、没有浏览器：**JSX 里的判据一条都没有回归网**。所以能算的全部下沉到这里，
由 `node --test` 钉住（先例：`worksheet-drag.ts`、`worksheet-editor-core.ts`）。

| 函数 | 判据 |
|---|---|
| `readPromptMarks(node)` | 校验 / 夹紧 / 排序 / 合并；坏数据不抛 |
| `markAt(marks, index)` | 光标处的合并样式 —— 工具栏 `is-active` 用它 |
| `rangeHasMark(marks, from, to, key)` | 选区**整段**都有这个标记吗（决定按下去是「设上」还是「取消」） |
| `setMarkOnRange(marks, from, to, patch)` | 切开重叠 + 合并相邻；`color` 覆盖 |
| `remapMarks(marks, prevText, nextText)` | **编辑之后挪区间** —— 最容易错的一处 |
| `segmentsOf(text, marks)` | 渲染用的分段（`PromptText` 用它） |

**`remapMarks` 先写成一张表再写代码**（前/后缀公共长度 ⇒ 被替换的区间 `[from, to)` ⇒
每条 mark 的情形）：完全在左 / 完全在右 / 被整个覆盖 / 跨两端 / 左端被切 / 右端被切 /
正好贴着边界。**这是本次唯一能真正自动验证的部分**，用例要先写、要有反证（改坏实现必须变红）。

## 渲染：一个实现，三处用（`src/lib/worksheet-prompt-text.tsx`）

导出 `<PromptText text marks />`，**只用行内样式、不带任何 CSS 模块类** —— 两个调用方分属
两套 CSS（学生端 `worksheet.module.css` 受 Safari 15 门禁扫，教师端 `globals.css`）。

消费者：**学生端面板**、**编辑页折叠预览**、**编辑器自己**。后两者与前者必须走同一份分段
（`segmentsOf`）—— 否则就是本仓最防的那种「预览里画得出来、学生那里画不出来，且两边都不报错」。

着重号：`-webkit-text-emphasis: filled dot` + `-webkit-text-emphasis-position: under`
（⚠️ **必须带前缀**）。⚠️ **中文字体的着重号字形不稳定** —— 有些字体根本不画。
这一条**只能真机看**，见下面的真机清单。

## 🔴 contenteditable 的五条硬约束（本次最大的风险）

裁定 ① 选的是三条路里**唯一会碰到中文输入法**的一条。下面五条不是「最好这样」，
是「少一条就会坏」：

1. **React 永远不许重渲这个框的子节点。** 内容只由 JS 写（首次挂载 / 换题时
   `dangerouslySetInnerHTML` 或直接 `replaceChildren`）。一旦 React 按 state 重画，
   输入法拼字会被打断 —— 🔴 **症状是「这个框没法打中文」**，而这个仓的用户全是中文教师。
2. **拼字期间（`compositionstart` → `compositionend`）一个字都不许回写**：不写 DOM、
   不让这个框跟着 setState 重渲。判据用 `event.nativeEvent.isComposing`。
   **这是唯一一条会让字段彻底不可用的约束。**
3. 🔴 **⌘Z 走的是本仓自己的历史栈**（`edit/page.tsx:178` 上面那段注释写着：那里**有意**
   抢掉浏览器的撤销，因为本仓每次改动一条、退掉的正是上一个字符）。它会把 `prompt` 换掉
   ⇒ 编辑器必须**把 DOM 重建成新文本**，并把光标放回一个**夹紧到新长度**的位置。
   ⚠️ 这件事 `<textarea>` 是**白拿的**（React 换 `value`，浏览器自己管光标），换成
   contenteditable 之后要自己做 —— **撤销之后光标跳回开头**就是漏了这一条的症状。
4. **换题（`node.id` 变了）整块重建**，不要试图 diff。
5. 保存仍走既有的 `onPromptChange` / `onDataChange` 与防抖队列，一个字节都不改。

⚠️ **键盘守卫**：`edit/page.tsx:198` 的 `↑/↓` 判据认的是 `[contenteditable="true"]` ——
React 写 `contentEditable` 会渲染成 `contenteditable="true"`，**对得上**；
写 `contentEditable=""` 就**对不上**，症状是打字时按上下键跳到别的题。

## 迁移（老数据的 `promptStyle`）

格式的来源从两个变成一个，这才是这一改真正的收益。
